# FINDINGS — тест хеш-адресации параметров (0x03/0xF8·0xF9)

Сессия 2026-08-03. Ветка `feat/param-hash-f8f9`.

## 1. Транспорт — воспроизведён и подтверждён на уровне кадра

Из профилей FreeFCC (`FreeFCC-main/app/src/main/assets/profiles/`):

- `led_on.json` / `led_off.json`: sender=2, cmd_type=0x40, порт **40007**,
  `wrapper=true`; кадр `s=3, i=249, d=3, p=a259ceed{ef|00}`.
- `fcc.json`: `8a237103f401` = write `max_height_0`=500 (0xF9); плюс ещё
  `236b8201`, `8773e68a`, `d04aeffb` (имена не подписаны).

`hashparam.py selftest` собирает LED-ON внутренний кадр:
```
55 12 04 c7 02 03 00 00 40 03 f9 a2 59 ce ed ef da 73
```
и обёртку:
```
55 cc 30 75 12 00 00 00  <inner>
```
— совпадает с тем, что строит `DumplBuilder` FreeFCC. Транспорт готов к живой
проверке (`probe --send`). Это **самая ценная и сразу проверяемая** часть находки:
работоспособность пути `0x03/0xF9` и `0x03/0xF8` не зависит от знания алгоритма
хеша, пока используются известные литеральные хеши (LED, max_height, GPS).

## 2. Алгоритм хеша — НЕ восстановлен

### 2.1 Опорные пары
| имя | on-wire | надёжность |
|---|---|---|
| `forearm_led_ctrl` | `a2 59 ce ed` | **высокая** — одинаков в led_on и led_off, меняется лишь байт значения |
| `max_height_0` | `8a 23 71 03` | средняя — из note автора fcc.json |
| `<GPS>` (0xF8 read) | `82 95 42 c5` | имя неизвестно, как якорь не годится |

### 2.2 Стратегия 1 — словарный перебор (`recover_hash.py dict`)
~17 стандартных функций (djb2/djb2xor/sdbm/java31/fnv1/fnv1a/jenkins-oat/elf/
crc32 ×5 вариантов/murmur3 ×2) × 5 форм строки (raw, raw+\0, lower, upper,
`g_config.`+name) по **1787** именам из `params/`. **Совпадений НЕТ** ни с LE, ни
с BE прочтением цели. Значит имя из наших дампов + стандартный хеш ≠ этим байтам.

### 2.3 Стратегия 2 — алгебраический взлом (`recover_hash.py affine`)
Для Horner-семейств (`h=h*M+c` и `h=(h+c)*M`) значение аффинно по `init`:
`h = M^n·init + P(bytes)`. Две опорные пары → перебор множителя `M` (curated +
все нечётные до 60000) × 3 формы имени × варианты пути `g_config.*`, `init`
решается через модульную инверсию. **Совпадений НЕТ.**

### 2.4 Вывод
Хеш **нелинейный / с финальным битмиксом** (djb2-xor, fnv1a, murmur, или кастом)
и/или с неизвестным seed — по двум точкам алгебраически не достаётся, среди
стандартных нет. Подтверждает исходную пометку находки: **алгоритм лежит в
`libdrone_hacks_lib.so`** (applet'ы `read_param_by_hash` / `write_param_by_hash`).

## 3. Якоря для следующей сессии (дизассемблирование .so)

`reference_app_2/lib/arm64-v8a/libdrone_hacks_lib.so` (21 МБ, arm64, **stripped**:
`.symtab` нет, только 245 динамических символов).

Найденные ориентиры (виртуальные адреса в `.text`/`.rodata`, посчитаны через
PT_LOAD-маппинг):

| строка | file off | vaddr |
|---|---|---|
| `duml-rust/src/applets/read_param_by_hash.rs`  | 3246270 | `0x3188be` |
| `duml-rust/src/applets/write_param_by_hash.rs` | 3401626 | `0x33e79a` |
| `duml::applets::write_param_by_hash::WriteParamByHash` | 3583269 | `0x36ad25` |
| CRC8-таблица (уже известна) | `0x13e2d28` | — |
| CRC16-таблица (уже известна) | `0x13e2f38` | — |

Прямой adrp+add поиск xref к этим строкам **не сработал**: Rust хранит
panic-location как статическую структуру `{ptr,len,line,col}` в `.data.rel.ro`,
а `.text` ссылается на *структуру*, не на строку. Следующий шаг:
1. Найти в `.data.rel.ro` указатель, равный vaddr строки → адрес Location-struct.
2. Найти adrp+add xref на Location-struct в `.text` → тело applet'а.
3. В applet'е перед сборкой payload будет вызов хеш-функции над `name`-slice
   (`ptr`,`len`). Дизассемблировать её (Ghidra/rizin даст читаемее, чем capstone).
4. Впаять восстановленный алгоритм в `hash_name()` в `recover_hash.py`, прогнать
   `python recover_hash.py verify` — должен дать `a259ceed`/`8a237103`.

Альтернатива без реверса: 60-сек USB/loopback-захват реального Drone-Hacks при
клике на параметр с известным именем — payload прямо покажет `hash(name)`; набрав
десяток пар имя→хеш, можно снова прогнать `affine_crack` и словарь по большему
набору форм имени, либо подобрать seed murmur/fnv.

## 4. Что это даёт приложению (если алгоритм найдётся)

`Duml.java`: добавить `writeByHash(name,value)` / `readByHash(name)` →
`hash_name(name)` + кадр `0x03/0xF9|0xF8`. Отпадает зависимость от
`ModelDb`/таблиц индексов и (для записи) от остановки DJI Fly, т.к. путь 40007+wrapper
у FreeFCC работает при живой DJI Fly. До восстановления хеша — держать хеши для
конкретных тумблеров (LED и т.п.) как литералы.
